# v0.7.0 — It survives a bad deploy

**Status: candidate.** This file is the scope proposal for the next milestone. It follows
`roadmap.md`'s rule — written against what is actually in the repo, not against what was planned —
and it will be folded into `roadmap.md` as a `## v0.7.0` section once the scope is agreed.

Three companions carry the rest: [`roadmap.md`](roadmap.md) is forward-looking,
[`backlog.md`](backlog.md) is everything known-broken with the evidence for each, and
[`history.md`](history.md) is what was learned doing the work.

---

## Why this release, and why this shape

`v0.6.0` shipped on 2026-09-03. Nineteen backlog entries closed, **twenty-eight remain open**, and
three facts about the repository decide what comes next.

**Two consecutive releases shipped no new capability.** v0.5.0 was debt paydown and v0.6.0 was an
audience release, and both said "no new capability" out loud and meant it. The README still
carries the row `RollbackDeployment, PatchResources — not built — refused, not attempted`, and
`roadmap.md` names the deferrals it was least comfortable with: `PatchResources` is *"the largest
gap"*, and the Slack channel is *"the harder call"*. A third freeze would be a decision about the
project rather than about the release.

**Every fault this agent can detect is one that was simply there.** All thirteen chaos fixtures
inject a steady-state fault and wait for it to be noticed. Not one of them performs a rollout or
creates a second revision — the only occurrence of the word "rollout" across all thirteen files is
an incidental comment about an update strategy in `c6-diskfill.yaml`. That is a real gap in what
the corpus can measure, because production incidents overwhelmingly start when something
*changes*, and a fixture with no history cannot ask the question every on-call engineer asks
first: **what changed?**

**And the machinery for answering that question is already built, and has never once fired.**
This is the finding the release is built on, and it is worth setting out in full because it
changes the size of the work:

| Piece | Status | Where |
|---|---|---|
| `ActionType.RollbackDeployment` | exists | `Core/Domain/Enums.cs:133` |
| Policy gate, with two tuned windows | exists, unit-tested | `Core/Policy/PolicyEngine.cs:393`, `PolicyEngineTests.cs:671-706` |
| `CurrentRevisionAge` / `PreviousRevisionHealthyFor` | gathered from ReplicaSet timestamps | `Pipeline/ClusterFactsGatherer.cs:176-190` |
| `get_rollout_history` read tool | exists | `Kubernetes/KubernetesReadTools.cs:576` |
| RBAC — `patch`/`update` on `deployments`, `list` on `replicasets` | **already granted** | `charts/hephaisto/templates/rbac-write.yaml` |
| Model-facing action description | written | `Investigation/PromptComposer.cs:355` |
| Runbook guidance for the sharp-onset case | written | `Runbooks/HighErrorRate.md:35` |
| Chart schema accepts it in `autoEnabledActionTypes` | yes | `charts/hephaisto/values.schema.json:79` |
| **The executor arm** | **missing — fails closed as `unsupported`** | `Core/Domain/ActionCapability.cs:37` |
| **A fixture that ever creates a second revision** | **missing** | — |

`HighErrorRate.md` has been telling the model *"Onset time is sharp → correlate with
`get_rollout_history`. A sharp edge is a deploy"* since it was written, and pointing it at
`rollback_deployment` as the strongest candidate — while `ActionCapability.IsImplemented` returns
false, so the planning prompt renders that action as **"Not available in this build."**

`ActionCapability.cs`'s own doc comment uses this exact scenario as the reason it exists:

> An operator could be shown an approval request for a `RollbackDeployment`, approve it, and watch
> it fail at execution with `outcome=unsupported` — a poor experience even though it is a safe
> one, and one that spends the scarcest thing in an incident, which is a human's attention.

So the gap is at the two ends: **an executor arm, and a fixture with a history.** The safety
argument in the middle was built a release ahead of the action, the way the policy engine itself
was.

## The two production failure modes this release was asked to cover

Both are change-shaped, and they are not the same size of work.

**A. An API stops returning successful requests after an update.** Error rate spikes; Kubernetes
reports the pod perfectly healthy throughout. **This ships.** `SignalKind.HighErrorRate` exists,
`ServiceHighErrorRate` and `ServiceCriticalErrorRate` are shipped SLO burn-rate rules,
`HighErrorRate.md` is a real runbook, and `infra/chaos/faulty-service/` is already an
OTel-instrumented ASP.NET app with a tunable `ERROR_RATE`, a traffic sidecar and a fully
correlated three-signal trail. What is missing is the *change* — nothing rolls out a second
revision — and the remediation.

**B. A service's throughput drops after an update — a Kafka consumer falling behind.**
**Deferred to v0.8.0, deliberately, and the reasoning is recorded here so it is argued once.**

It is entirely greenfield: `grep -ri 'kafka|redpanda|consumer.lag'` across the repository returns
nothing but an incidental pod name in a recorded transcript. It needs a broker in the chaos
namespace (the first runtime dependency ever added there), a producer, a consumer whose second
revision is slower, a new `SignalKind` **and its runbook in the same commit**, new alert rules,
and a scrape path that attaches the *consumer's* namespace rather than the exporter's.

The part that makes it a release rather than a fixture is verification.
`VerificationChecks.WorkloadIsHealthyAsync` reports **Passed** for a consumer that has been
scaled up while its lag is still climbing — every replica is Ready and nothing restarted. An
action that verifies green while the incident continues is the one failure mode this project's
safety argument cannot tolerate, and fixing it means `VerificationChecks` reaching outside the
Kubernetes API to Prometheus for the first time. That is a design decision, not a line of code.

It is also the c10 trap one layer down, and c10 is the fixture whose header comment already
teaches it: *"an events-only or kubectl-only agent sees a green pod and reports 'no issues found',
which is wrong."*

## What ships

### Features

#### F1 — `RollbackDeployment`, the executor arm — **M** — half of [#39](backlog.md#39)

The remediation for A. Small, because everything around it exists.

- `Core/Domain/ActionCapability.cs` — add the member to `IsImplemented`. This one line flips the
  planning prompt from *"Not available in this build."* to an action the model may propose.
- `Pipeline/ActionExecutor.cs` — a `RollbackDeploymentAsync` arm. A Deployment's history *is* its
  ReplicaSets: find the previous one by the `deployment.kubernetes.io/revision` annotation and
  patch `spec.template` back. There is no `rollback` subresource in modern Kubernetes, which is
  why the existing `patch`/`update` grant is already sufficient. **Route the dry-run through the
  existing `dr` variable** — every arm does, so that a new action type cannot forget it.
- `Pipeline/VerificationChecks.cs` — this closes [#42](backlog.md#42)'s half, and the predicate
  matters. It is **not** "the workload is Ready" but "Ready **and on the revision we asked for**".
  A rollback that silently no-ops must not verify green, which is the same failure-toward-yes that
  cost v0.2.0 three bugs.
- `Pipeline/ActionRollback.cs` — decide whether the inverse (roll forward) is offered, or whether
  the default stands.
- **No RBAC change, no policy change, no prompt change.**
- Promote `RollbackFreshRevisionWindow` and `RollbackPreviousHealthyMinimum` to first-class chart
  values. They are code defaults today with no mention in `values.yaml` — a fresh instance of
  [#22](backlog.md#22)'s class, and the moment this ships they become the two knobs an operator
  most needs to reach.

Tests: `ActionExecutorTests.cs:75` currently asserts this type is *refused* and must invert;
`PolicyEngineTests.cs` already covers the gate.

#### F2 — `c14-bad-deploy`, the first fixture with a history — **M**

Reuses `infra/chaos/faulty-service/` unchanged. Revision 1 at `ERROR_RATE=0.0`, healthy long
enough to satisfy `RollbackPreviousHealthyMinimum`; then revision 2 at a high error rate. The
error spike and a fresh ReplicaSet share a timestamp, which is the whole point.

**This is the main design risk in the release**, and it should be prototyped before anything else
is written. It is the first fixture whose *setup has a timeline* — the chaos phase today applies
manifests and waits — and the dwell between the two revisions interacts directly with the two
policy windows (`RollbackFreshRevisionWindow` 30m, `RollbackPreviousHealthyMinimum` 1h). Get it
wrong and the policy engine refuses for a **correct** reason and the fixture proves nothing, which
is exactly the ambiguity `c13` was created to escape ([#90](backlog.md#90)). It may well argue for
changing the window defaults rather than bending the fixture around them.

Harness wiring — these tables must be extended together or the fixture is silently dropped:

- `scripts/e2e/lib/chaos.sh` — `FULL_FIXTURES`, the fixture→`SignalKind` case, a detection timeout
  sized for the 5-minute rate windows, and a `chaos_build_images` case.
- **`fixture_target()`, which is the one that bites.** c10 maps to `faulty-service` rather than a
  `c<N>-` name prefix, because a span-metrics series identifies the workload only as `service:`.
  [#33](backlog.md#33) fixed the *namespace* half of that; the *name* half is permanently
  unrecoverable. Getting this wrong is what reported c10 as undetected across two release
  candidates while its incident existed the whole time. c14 has the identical shape.
- `scripts/e2e/lib/judge.sh`'s `fixture_truth()` **and** `src/Hephaisto.Eval/Scoring/AnswerKey.cs`
  — `AnswerKeyParityTests` enforces that they agree. `AcceptableActions = [RollbackDeployment]`,
  which makes c14 the **first fixture in the corpus where a non-restart action is the right
  answer**: c11, c12 and c13 all accept `[RestartPod, RolloutRestart]` and nothing else.
- `infra/chaos/README.md` — the table, which is the contract the regression suite is written
  against.

#### F3 — Change correlation — **M**

`roadmap.md`'s "Later" menu, item four: *"this started 4 minutes after the rollout of `x:sha`"*.

The narrow version, which is the one worth building: surface rollout history as a **fact in the
incident card** rather than only as a tool the model may or may not think to call. An incident on
a workload whose current revision is minutes old should say so without spending a step to discover
it.

That framing is not a convenience. [#74](backlog.md#74) established that step budget is the
binding constraint on accuracy, and [#88](backlog.md#88) found nine runs that ended on a budget
before the planner ran at all. **A fact given for free is a step not spent**, and this is the fact
that makes the difference between a rollback that is a reasoned response and one that is a guess —
which is the distinction `PromptComposer`'s own description of the action already draws.

#### F4 — The console renders an action's verifications — **S** — [#96](backlog.md#96)

The one item already assigned to this milestone. `AgentAction.Verifications` carries the T+60s /
T+5m / T+15m outcomes, is persisted, and is read by nothing on the way out.

It matters more than its size suggests: **"everything it does is verified, then reverted if it did
not work" is on the public landing page**, and the evidence that it happened lives only in the
database and the logs. The one screen a human looks at an action on is the one place the check on
that action is not shown.

Three parts, and the third is the one that would otherwise be forgotten:

1. `IncidentDetail.razor` renders the verification rows.
2. `hephaisto-eval export` carries them into transcripts. It deliberately does not today, on the
   sound grounds that an artifact should not ship fields with no consumer; that reasoning expires
   the moment part 1 lands.
3. **`design/gallery.html` gains the component.** `CLAUDE.md` is explicit: *"If you change a
   component, change it in the gallery too, or the net stops covering it."* The gallery today
   photographs the incident row, the finding, the budget meters, tokens, callouts, forms, code and
   the focus ring — and **none** of the action, plan, policy-decision, timeline or step-trace
   components that the incident detail page is actually made of.

#### F5 — Runbooks for the kinds that ship without one — **S**

`SignalKind` has eighteen members and `Runbooks/` has ten files plus `_Default.md`.
`HighLatency`, `TargetDown`, `ReplicaMismatch` and `RestartStorm` all have **shipped alert rules**
and fall through to the default runbook, which is entirely Kubernetes-shaped — *who owns this,
get_events, get_pod_logs previous:true* — and useless for a burn-rate alert on span metrics.

The enum's own doc comment states the contract: *"adding a member means adding a runbook."* These
four predate the rule.

`HighLatency` is the one this release needs. It is c10's other signal, it is half of failure mode
A, and `HighErrorRate.md` — whose title is literally *"High error rate / high latency (span
metrics)"* — already covers it and is simply unreachable from the kind.

Note that this moves `HighLatency` from the `Falls_back_to_the_default_runbook` theory to
`Picks_the_runbook_for_the_signal_kind` theory in `PromptComposerTests.cs`, and needs a
`docs-site/internals/runbooks/` stub and index row.

#### F6 — An absent allowlisted tool is loud — **S** — [#31](backlog.md#31)'s cheap half

`grafana-mcp` ships started with Tempo unconfigured, so four allowlisted tools are never
registered:

```
grafana-mcp offers 44 tools; 4 allowlisted tools are absent:
  query_tempo_traces, query_tempo_traceql, list_tempo_tag_names, list_tempo_tag_values
```

That line is logged at `Information` and reads like routine startup noise. The consequence is
that **c10 — the fixture whose header calls it "THE IMPORTANT ONE", built to prove
alert → exemplar → trace → log → cause — cannot reach hops 2, 3 and 4.** Measured on 2026-08-29:
recording c10 spent **13 steps and 16 tool calls and produced no primary finding**, the only
fixture of eight to produce none, and every `gpt-oss` replay of c10 still scores `NoFinding`.

Make the absence a **warning that names the capability being lost**. Wiring an actual Tempo MCP
server is the M half and stays deferred — it is the obvious companion to the v0.8.0 messaging
work, where trace correlation is the whole point again.

### What does not ship, and why

**`PatchResources`**, [#39](backlog.md#39)'s other half. It is the actual remediation for c4 and
c7 — the two fixtures where diagnosis succeeds and the planner has nothing to offer — and it is
named again here because that is *why* those two are permanently "diagnose correctly, propose
nothing". It needs a restricted, typed vocabulary (container image, resource limits) rather than
an arbitrary merge patch, because applying a model-authored JSON patch verbatim would hand the
model the mutating handle the three-phase split exists to deny it. Doing both halves of #39 in one
release makes the executor the whole release.

**Failure mode B**, for the reasons given above.

**[#23](backlog.md#23)**, NetworkPolicy enforcement. It needs Calico under kind; it is an
`--enforce-netpol` tier rather than a fix, and it remains the harness's own printed uncovered
limit.

## What this does for the corpus

The release was asked for more realistic tests. Concretely:

**The demo stops showing one fault.** The corpus today is twelve transcripts: ten replays, every
one carrying `promptFreshness: STALE` ([#80](backlog.md#80)), and **two cluster captures that are
the same fixture twenty-five minutes apart** — so the site that says *"It fixes what it can
prove"* shows exactly one fault the agent acted on, one action type, and one of its two real pages
is mislabelled by [#70](backlog.md#70). c14 adds a second real acted-on incident, on a **different
action type**, with a cause that happened at a time — exported through `hephaisto-eval export` the
way c13 was. F4 makes its verification rows visible, which is the half of the safety argument the
demo currently cannot show at all.

**The acting gate stops being one action on one fixture.** Four of the six executable
`ActionType`s have no fixture: `ScaleWorkload`, `DeleteStuckJob`, `DeleteFailedJobPods` and
`SilenceAlert`. c14 covers a fifth. **A cheap adjacent win worth taking in the same pass: `c5`
already exists, is the obvious `DeleteStuckJob` / `DeleteFailedJobPods` fixture, and has no
`AcceptableActions` in the answer key** — adding them widens acting coverage by a third for one
line of JSON.

**Known-uncovered, and recorded rather than fixed here**, because naming them is worth more than
half-doing them: the approval *click* path has no cluster coverage (`acting.spec.ts` fills the
actor field and asserts the button enables — it never clicks it), so `RequireApproval → Approved →
Executed` is unproven end to end; oscillation and cooldown are unit-only; `Search.razor` has no
test of any kind; and nothing asserts anything about the rendered demo HTML beyond "at least
twelve files exist".

## Done when

An error-rate spike that began at a rollout is detected, correlated to the revision that caused
it, remediated by a `RollbackDeployment` that the policy engine admitted on its freshness gate and
the executor carried out, and verified through to `Resolved` — **observed on a cluster, with the
run's assertion count and duration recorded the way c13's were**, and exported as a transcript the
demo site renders with its verification rows visible.

The release gate becomes three runs rather than two, extending [#97](backlog.md#97) rather than
contradicting it:

```sh
scripts/e2e/run.sh --tag <version> --full                        # diagnosis
scripts/e2e/run.sh --tag <version> --fixtures c13 --mode Auto    # acting: RestartPod
scripts/e2e/run.sh --tag <version> --fixtures c14 --mode Auto    # acting: RollbackDeployment
```

Per #97 the acting assertion cannot pass inside a `--full` run — simultaneous fixtures cross
`policy.clusterUnhealthyCeiling` and the policy engine correctly refuses every action as a
cluster-wide event. **That is a working safety gate and must not be "fixed" by widening the
ceiling.**

[#103](backlog.md#103) has a verification that needs no cluster and should be done first: render
the chart with default values against a stack that has never run c10, and confirm
`ServiceNoTraffic` does not fire. Today it will.
